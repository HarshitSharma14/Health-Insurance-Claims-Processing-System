# Kiro Setup — Plum AI Engineer Assignment

## What's in here
```
.kiro/steering/
  product.md            (always)  — the assignment spec, condensed, with grading weights
  architecture.md       (always)  — locked-in multi-agent design
  tech-stack.md         (always)  — language/framework/LLM/db choices — EDIT THIS FIRST
  data-contracts.md     (fileMatch: schemas/models/agents) — I/O schemas per component
  observability.md      (always)  — trace schema + explainability rules
  error-handling.md     (always)  — graceful degradation rules per failure mode
  testing.md            (always)  — test coverage expectations + eval harness
  coding-standards.md   (always)  — commit hygiene, code style, assumptions log
  specs-workflow.md     (manual)  — how to drive Kiro's spec workflow per component
```

## How to use this

1. **Copy `.kiro/` into the root of your project repo.**

2. **Drop in the assignment's resource files** at the project root:
   `policy_terms.json`, `test_cases.json`, `sample_documents_guide.md`.
   Then open `policy_terms.json` and `test_cases.json` and skim them —
   `architecture.md`'s policy-evaluation checks and `error-handling.md`'s
   confidence thresholds are written generically; adjust the specifics
   (exact field names, check names) to match the real file once you've seen
   it. Same for `data-contracts.md` if the document types in
   `sample_documents_guide.md` differ from the placeholders used there.

3. **Edit `tech-stack.md` first** if you want a different stack than the
   default (Python/FastAPI/Pydantic/React) — Kiro will follow whatever is
   written there.

4. **Start a chat with Kiro** and ask it to read the steering files and
   propose/refine `architecture.md` based on the actual `policy_terms.json`
   and `test_cases.json` contents. Let it suggest edits to that file before
   writing any code.

5. **Run the spec workflow** per `specs-workflow.md` (type `#specs-workflow`
   in chat to pull it in), one component at a time, in the suggested order.

6. **Set up hooks** (optional but recommended):
   - On save of any file under `app/agents/**` or `app/orchestrator/**` →
     run the matching pytest file.
   - On save of any file under `app/schemas/**` → remind/regenerate the
     Component Contracts doc section for that schema.

7. **At the end**, the architecture document and component contracts
   deliverables can largely be assembled from `architecture.md`,
   `data-contracts.md`, and the `design.md` files generated by each spec —
   tidy them up rather than writing from scratch.

## A note on the "multi-agent bonus"
The architecture here already treats document verification, extraction,
policy evaluation, and decision-making as separate agents/components with
explicit contracts and a shared trace — that's the multi-agent structure the
bonus criteria reward. Keep them genuinely separable (each independently
testable and replaceable) rather than one big function split across files in
name only.
